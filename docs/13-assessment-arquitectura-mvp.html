01 Stack y capas — arquitectura general 6 puntos
#Punto de evaluaciónEstadoImplicación / acción
01.1
Separación de capas: dominio puro vs. persistencia vs. UI
El diseño define capas explícitas: domain/ (tipos + reglas + transiciones), data/ (repositorio + reloj), features/ (UI + lógica de presentación). El dominio no importa ni localStorage ni React. La UI no escribe directamente a storage.
 ✅ LISTO Arquitectura implementada y aprobada en C2–C3. Contrato §9 cumplido. Sin deuda técnica aquí.
01.2
Motor temporal determinista como agente del sistema
El temporalEngine.ts / demoClock actúa como actor del sistema (no usuario), emite eventos ROUND_DUE, ROUND_OVERDUE, ALERT_CREATED, CLOCK_ADVANCED. Separado del flujo de usuario.
 ✅ LISTO Aprobado en C7. Escenarios deterministas y reproducibles. El reloj simulado permite demo en <5 min.
01.3
Persistencia vía capa repositorio — UI nunca toca localStorage directamente
Regla del contrato §6 punto 9: solo repository.ts puede leer/escribir localStorage. Los componentes React llaman al repositorio, nunca a window.localStorage directamente. Verificable con grep.
 ✅ LISTO Cumplido en C3. Si se detecta una violación, es un blocker de arquitectura.
01.4
Diseño de producción: GCP Cloud Run + Firebase + PostgreSQL (v0.2)
El documento de arquitectura describe la transición: localStorage (demo) → PostgreSQL en GCP Cloud Run + Firebase Auth (producción). El stack de producción está documentado en §09, §10 y en el memory del proyecto.
 📐 DISEÑO OK Solo diseño — no se implementa en MVP. El pitch debe presentar este stack para mostrar la ruta de producción ante los jueces.
01.5
TypeScript estricto sin any — verificable
Contrato §9: TypeScript strict, sin any. El CI (npm run typecheck) verifica esto. 38/38 pruebas automatizadas pasan. El tsconfig tiene strict: true.
 ✅ LISTO C8 auditó esto. Verificar que no se haya roto tras los últimos cambios de E-track si se edita código.
01.6
Pipeline de build para demo pública: npm run build → dist/ → GitHub Pages
El MVP debe servirse como demo interactiva en GitHub Pages para la competencia. El dist/ debe generarse, subirse al repo público y activar GitHub Pages. Actualmente no hay remoto configurado.
 🔨 PENDIENTE Bloqueador de E3. Requiere: repo GitHub creado, npm run build, push de dist/, activar Pages. Sin esto los jueces no pueden ver la demo en vivo.
02 Multi-tenant — aislamiento por residencia 6 puntos
#Punto de evaluaciónEstadoImplicación / acción
02.1
residencia_id como tenant isolator en todas las entidades
El data model define residencia_id como FK obligatoria en habitaciones, residentes, staff_members, rondas, alertas, incidentes, audit_events. Ninguna entidad existe fuera de una residencia.
 ✅ LISTO Diseño correcto. En el MVP (localStorage) el aislamiento es por sesión. En producción, RLS en PostgreSQL lo enforza a nivel DB.
02.2
Cardinalidades y relaciones documentadas (1:N, 1:0..1)
El diagrama de árbol y la tabla de cardinalidades en §02 especifican: residencia→habitaciones (1:N), habitacion→residentes (1:N), residente→rondas (1:N), ronda→alerta (1:0..1), alerta→incidente (1:0..1), cualquier entidad→audit_events (1:N).
 ✅ LISTO La restricción "una ronda máx. una alerta activa" está implementada en rules.ts. Verificar que el seed data respete estas cardinalidades.
02.3
Datos ficticios de una sola residencia demo en el seed
El seed.ts crea datos ficticios para una residencia demo. No hay datos reales de personas. El aviso "Datos ficticios" debe ser visible en la UI.
 ✅ LISTO Aprobado en C3. Verificar que el aviso "MVP operacional, no dispositivo médico" + "Datos ficticios" sea visible en todas las páginas (contrato §1).
02.4
Ningún dato cruza entre residencias — enforced en repositorio
El repositorio filtra siempre por residencia_id de la sesión activa. En el MVP la sesión ficticia define el tenant. Ninguna función del repositorio acepta un residencia_id diferente al de la sesión.
 ✅ LISTO En producción esto se refuerza con Row-Level Security en PostgreSQL y middleware de autenticación. Para el pitch: presentar esto como diferenciador de seguridad.
02.5
Modelo de planes de suscripción (esencial / profesional / institucional) en diseño
La tabla residencias tiene el campo plan ENUM('esencial','profesional','institucional'). El diseño de precios por plan está en el dossier ejecutivo pero no está implementado en el MVP (sin feature flags por plan).
 📐 DISEÑO OK No se implementa en MVP. El campo existe en el schema para habilitar feature gating en v0.2. Suficiente para el pitch como evidencia de modelo de negocio.
02.6
Escalabilidad multi-residencia — demostrable en pitch, no en MVP
El diseño soporta N residencias como tenants independientes. La demo muestra una sola residencia. El juez necesita ver que la arquitectura es multi-tenant por diseño, no por accidente.

03 Evento core — ciclo de vida de la ronda 6 puntos
#Punto de evaluaciónEstadoImplicación / acción
03.1
Máquina de estados completa: scheduled → due → in_progress → completed
El flujo principal del cuidador completa en ≤3 acciones (C5). Las transiciones están en transitions.ts y son la única ruta válida — ningún componente puede cambiar un estado directamente.
 ✅ LISTO 20/20 pruebas de aceptación pasan. Camino feliz funcional end-to-end para el cuidador.
03.2
Ruta de fallo: due → overdue → ALERT generada automáticamente
Cuando el motor temporal detecta que una ronda pasó su tiempo límite sin ser iniciada, la pasa a overdue y genera una alerta. Esta es la ruta narrativa central del pitch (fallo operativo = dato sin registrar).
 ✅ LISTO C7 aprobado. El escenario de demo lo activa en <2 minutos con el reloj simulado. Esencial para mostrar valor en los 4 minutos del pitch.
03.3
Transiciones inválidas retornan error controlado — no corrompen datos
Intentar completed → overdue o cancelled → cualquiera devuelve un error de dominio, no silencia ni corrompe. Regla del contrato §6 punto 8.
 ✅ LISTO Verificado en tests. Esta propiedad es el argumento de confiabilidad ante los jueces: el sistema no acepta estados imposibles.
03.4
5 tipos de ronda operativos (lookup) — ninguno con lenguaje médico
routine_check, hydration_check, mobility_assistance, meal_assistance, custom_operational_check. Sin "diagnóstico", "evento clínico" ni términos prohibidos del contrato §6.
 ✅ LISTO El aviso "operacional, no médico" es clave para el concurso (IMSS / SSA no son clientes directos). Los tipos de ronda actuales son correctos para el mercado privado de residencias.
03.5
Resultado de ronda registrado al completar — trazabilidad operativa
Al completar una ronda el cuidador puede registrar un resultado (texto libre). Este resultado es parte del audit_events y se refleja en el historial visible para el supervisor. Es la evidencia que protege a la residencia ante una queja.
 ✅ LISTO Vinculado al argumento legal (NOM-031-SSA3-2012): la bitácora con resultado es el expediente operativo. Mencionar en el pitch.
03.6
Una ronda no puede tener dos alertas activas simultáneas
Regla del contrato §6 punto 2: ronda → alerta (1:0..1) activa. Si la ronda ya tiene una alerta open o assigned, el motor no genera una segunda. Verificado en rules.ts.
 ✅ LISTO Esta invariante es crítica para la integridad del dashboard: evita duplicados que confundirían al supervisor durante la demo.
04 Data model — 9 tablas relacionales 6 puntos
#Punto de evaluaciónEstadoImplicación / acción
04.1
9 tablas documentadas con tipos, llaves y notas de integridad
residencias, habitaciones, residentes, staff_members, ronda_tipos, rondas, alertas, incidentes, audit_events. PK, FK, UK, IDX definidos. Columnas nullable explicitadas.
 ✅ LISTO Documento de arquitectura §04 es la fuente de verdad para la migración de schema en v0.2. Suficientemente detallado para que un DBA lo implemente en PostgreSQL sin ambigüedades.
04.2
estado_visual del residente: derivado, nunca persistido
El color del residente (🟢🟡🔴) es calculado por deriveResidentStatus() — función pura. No tiene columna en la DB. Si se persistiera, podría quedar desincronizado con el estado real de las rondas y alertas.
 ✅ LISTO Propiedad de diseño correcta. Verificar que ningún componente intente persistir este campo (búsqueda en código: estado_visual en escrituras al repositorio).
04.3
Índices compuestos definidos para las consultas principales
El índice (residencia_id, estado, programada_at) en rondas cubre la consulta principal del dashboard y el motor temporal. (residencia_id, created_at DESC) y (entidad_tipo, entidad_id, created_at DESC) en audit_events cubren el log y el historial por entidad.
 📐 DISEÑO OK No aplica en MVP (localStorage no tiene índices). Son el mapa de performance para v0.2 en PostgreSQL. Sin estos índices el dashboard con 100+ residentes sería lento.
04.4
IDs estables como strings (UUID) — sin IDs numéricos secuenciales
Contrato §9: IDs estables como strings. UUIDs garantizan que el mismo objeto tenga el mismo ID en todos los entornos (seed, tests, localStorage, producción futura), sin colisiones en merge de datos.
 ✅ LISTO El seed usa IDs prefijados (ej. "resident-001"). En producción usar gen_random_uuid(). La referencia cruzada entre audit_events y la entidad depende de la estabilidad del ID.
04.5
Alertas: resolved_at requerido antes de closed_at — integridad de ciclo
La columna closed_at en alertas solo puede poblarse si resolved_at ya existe. Regla del contrato §6 punto 5. El repositorio y las transiciones deben enforcar esto, no la DB sola.
 ✅ LISTO Verificado en C6. Esta regla es el argumento de integridad: "no se puede cerrar lo que no se verificó". Clave para el argumento legal ante inspección.
04.6
Migración de schema de localStorage a PostgreSQL — path documentado pero no implementado
El data model de §04 es la spec del schema PostgreSQL de producción. Sin embargo, no hay un script de migración (.sql) ni un ORM configurado. La transición es un gap de implementación para v0.2.
 ⚠️ BRECHA Para la competencia: no es necesario implementarlo. Sí es necesario mencionarlo como "path claro a producción". Opcional: agregar un archivo docs/schema.sql generado del data model como evidencia técnica.
05 Catálogo de eventos — 20 tipos (event sourcing) 6 puntos
#Punto de evaluaciónEstadoImplicación / acción
05.1
20 tipos de evento cubren el ciclo operativo completo
7 ROUND_*, 8 ALERT_*, 3 INCIDENT_*, 2 sistema (DEMO_RESET, CLOCK_ADVANCED). Cada transición de estado del dominio tiene su evento correspondiente. No hay transición sin evento.
 ✅ LISTO El catálogo está documentado en §05 y es la base del audit log. Cualquier extensión futura (nuevos flujos) requiere agregar nuevos tipos — no modificar los existentes.
05.2
Audit log append-only — ningún UPDATE ni DELETE en audit_events
La restricción más importante del sistema. audit_events es el registro permanente requerido por NOM-031-SSA3-2012. En la UI no existe ninguna función de edición del log. En producción, los permisos de DB deben restringir a INSERT-only en esta tabla.
 ✅ LISTO Esta propiedad es el argumento más fuerte ante un inspector o en un proceso legal. "El log no se puede modificar retroactivamente" = evidencia confiable.
05.3
Cada evento lleva actor_id + timestamp + payload estructurado
Columnas: actor_id (NULL para sistema), created_at (NOT NULL), payload JSONB (schema libre por tipo). Permite reconstruir el historial completo de cualquier entidad filtrando por entidad_tipo + entidad_id.
 ✅ LISTO En localStorage el payload se serializa como JSON. En producción, JSONB de PostgreSQL permite queries sobre el payload (ej. "todas las reasignaciones donde nuevo_owner = X").
05.4
Esquema del payload por tipo de evento — no documentado formalmente
Los 20 tipos de evento están nombrados pero el schema interno del payload (qué campos lleva cada tipo) no está documentado como contrato. Ejemplo: ¿qué lleva ALERT_REASSIGNED? ¿{prev_owner_id, new_owner_id, reason}?
 ⚠️ BRECHA Para el MVP demo no es bloqueante — los payloads están en el código. Para v0.2 es crítico: cualquier agente de IA (A2, A3) que consuma el audit log necesita saber exactamente qué esperar en cada payload.
05.5
Separación semántica: eventos de usuario vs. eventos del sistema
Los eventos DEMO_RESET y CLOCK_ADVANCED tienen actor_id = NULL y marcan acciones del motor temporal, no de un humano. Esta distinción es esencial para el agente A2 de ciberseguridad: un acceso fuera de turno de un humano vs. una transición automática del sistema son patrones muy diferentes.
 ✅ LISTO El diseño es correcto. Para el pitch: "podemos detectar comportamiento anómalo porque distinguimos qué hizo el sistema de qué hizo un humano."
05.6
Event sourcing como insumo de ML/IA — arquitectura preparada pero datos aún vacíos
La arquitectura de audit_events fue diseñada para ser el dataset de entrenamiento de futuros modelos ML (sección §10). Sin embargo, en v0.1.0 solo hay datos ficticios del seed — sin operación real, no hay señal para entrenar.
 📐 DISEÑO OK La arquitectura está preparada. El pitch debe presentar esto como "infraestructura que habilita IA futura" — no como "tenemos IA hoy". Los agentes A2 y A3 de la sección 10 son el siguiente paso natural.

El gerente tiene vista ejecutiva: incidentes, historial completo de alertas, log de auditoría, exportar bitácora. Es el rol que "cierra el ciclo" ante una inspección regulatoria.

Cubre 6 categorías: Residentes, Rondas, Alertas, Incidentes, Staff, Auditoría/Métricas, Configuración. 4 roles (Cuidador, Supervisor, Gerente, Demo Admin). Distingue acceso completo, parcial y denegado.
 ✅ LISTO Añadida en esta sesión. Junto con la tabla "NO puede ver", es la evidencia de RBAC para el argumento de ciberseguridad ante los jueces.
06.6
Demo Admin: control del reloj simulado y reset del demo — funcional
El Demo Admin puede avanzar el reloj, activar escenarios (ronda overdue en 2 min), y hacer reset. Este control es lo que permite una demo de 4 minutos en vez de esperar tiempos reales.
 ✅ LISTO Aprobado en C7. El script de demo debe incluir los pasos exactos: qué botón presionar, qué pantalla mostrar, en qué momento. Verificar que el escenario determinista se puede reproducir idénticamente.
07 API layer — endpoints y contratos de mutación 6 puntos
#Punto de evaluaciónEstadoImplicación / acción
07.1
Endpoints de rondas documentados: GET, POST, PATCH start/complete/cancel
5 operaciones sobre rondas documentadas en §07. En el MVP el "API layer" es la capa del repositorio (repository.ts). En producción serán rutas HTTP REST en Cloud Run.
 📐 DISEÑO OK El contrato de API está documentado. No se implementa como HTTP en el MVP. Para v0.2, el repositorio se reemplaza por llamadas fetch a estos endpoints — sin cambiar las llamadas desde los componentes React.
07.2
Endpoints de alertas: acknowledge, assign, escalate, start-verification, resolve, close
7 operaciones sobre el ciclo de vida completo de la alerta. Cada endpoint corresponde a una transición de estado en transitions.ts. El body de /resolve requiere resultado_verificacion.
 📐 DISEÑO OK El diseño es correcto y completo. La separación de endpoints por transición (no un PATCH genérico de estado) es una decisión de diseño defensiva: hace imposible saltar transiciones desde la red.
07.3
Patrón de mutación: validar transición → escribir → insertar audit_event en una sola operación atómica
Cada mutación sigue el mismo patrón de 3 pasos: (1) validar en domain, (2) escribir a tabla, (3) insertar en audit_events. En producción los 3 pasos son una sola transacción de DB. En el MVP son 3 operaciones de localStorage.
 ✅ LISTO El patrón está implementado en el repositorio del MVP. En localStorage la atomicidad es eventual (no hay transacciones). En PostgreSQL será una transacción real — sin riesgo de audit_event sin el cambio de estado correspondiente.
07.4
Endpoint interno del motor temporal: POST /internal/tick
El motor temporal no está expuesto al cliente. En producción es un cron que llama a un endpoint interno de Cloud Run. En el MVP es una función del demoClock que se activa manualmente o por el Demo Admin.
 ✅ LISTO La separación "endpoint interno vs. público" es correcta desde el punto de vista de seguridad. En producción, este endpoint solo es accesible desde Cloud Scheduler, no desde internet.
07.5
Rate limiting, autenticación JWT y RBAC por endpoint — no implementados en MVP
El diseño de producción en §09 describe Firebase Auth (JWT), middleware RBAC por endpoint y rate limiting en Cloud Run. Nada de esto existe en el MVP (no hay backend HTTP).
 🚫 FUERA DE ALCANCE Correcto que no estén en el MVP. Para el pitch: describir el diseño de seguridad de producción como "paso siguiente claro" sin fingir que ya existe.
07.6
Endpoint de auditoría con filtros por entidad y por rango de fechas — diseñado, no implementado como HTTP
GET /audit?entidad_tipo=ronda&entidad_id=:id y GET /audit?desde=ISO&hasta=ISO (solo gerente). En el MVP el repositorio ya implementa la consulta equivalente sobre localStorage.
 📐 DISEÑO OK La equivalencia MVP→producción es directa. El segundo endpoint tiene restricción de rol explícita en el diseño — es el argumento de "el gerente tiene acceso completo, el supervisor no".

09 Ciberseguridad — diseño, RBAC y marco legal 6 puntos
#Punto de evaluaciónEstadoImplicación / acción
09.1
Privacidad por diseño en v0.1.0: datos nunca salen del dispositivo
No hay API externa, no hay sincronización, no hay telemetría. El dato más seguro es el que nunca viaja. Esta decisión arquitectónica es la mejor defensa posible para un MVP sin infraestructura de seguridad.
 ✅ LISTO Argumento de seguridad paradójico pero correcto: "la superficie de ataque de la red es cero porque no hay red." Diferenciador ante jueces de ciberseguridad — no es debilidad, es decisión de diseño declarada.
09.2
RBAC documentado: qué puede y no puede ver/hacer cada rol
Las tablas "SÍ puede ver" y "NO puede ver" en §06 cubren las 6 categorías de datos. Las restricciones están implementadas en el repositorio (no solo en la UI). Un cuidador no puede llamar a getAuditLog() aunque intente hacerlo desde la consola.
 ✅ LISTO Para el concurso de ciberseguridad: mostrar el RBAC como feature, no como implementación interna. "Cada rol ve exactamente lo que necesita y nada más" es el principio de mínimo privilegio en acción.
09.3
Marco legal documentado: LFPDPPP + NOM-031-SSA3-2012 + LGS Art. 419
Tres normas aplicables con su obligación concreta y cómo CareSignal la cumple. El audit log append-only cumple el expediente operativo permanente de NOM-031. La bitácora es la evidencia ante LGS Art. 419.
 ✅ LISTO Este es el diferenciador de credibilidad ante compradores institucionales. El pitch menciona la carga administrativa — conectar explícitamente con estas normas en el slide de marco legal.
09.4
Arquitectura de seguridad de producción: TLS + Firebase Auth + RLS documentada
El diagrama de capas en §09 describe: perímetro (TLS, JWT, RBAC middleware), datos en reposo (AES-256 GCP), datos en tránsito (TLS 1.3), RLS por residencia_id en PostgreSQL.
 📐 DISEÑO OK No implementado (no hay backend). El diseño es suficientemente detallado para presentarlo a jueces técnicos. Incluir el diagrama de capas en el deck o en el dossier.
09.5
Sin secretos en el código — verificable en el repo público
El MVP no tiene API keys, tokens ni credenciales hardcodeadas. No hay .env con valores reales. El repo público puede inspeccionarse sin exponer ningún secreto.
 ✅ LISTO Verificar con git log --all -- '*.env' antes del push público para confirmar que ningún commit pasado incluye un .env con valores. Punto sensible ante un juez de ciberseguridad.
09.6

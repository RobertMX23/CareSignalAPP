§5 Gaps y divergencias consolidados — prioridad y acción recomendada 4 gaps · 7 divergencias
GAP-01audit_event ausente de ENTITY_TYPES en taxonomy.ts🔴 GAP
Problema: La entidad audit_event está definida en docs/01-domain-taxonomy.yaml (entities[]) y tiene su interfaz AuditEvent en types.ts, pero NO está en el array ENTITY_TYPES de taxonomy.ts. El tipo EntityType solo cubre 5 entidades (resident | staff_member | round | alert | incident).
Impacto: AuditEvent.entityType no puede tomar el valor 'audit_event' si alguna vez se quisiera emitir un evento sobre el propio log. El type guard isEntityType('audit_event') retorna false.
→ Acción: agregar 'audit_event' a ENTITY_TYPES en taxonomy.ts. Es un addendum menor, no un cambio de contrato.
GAP-02VerificationOutcome ausente en docs/01-domain-taxonomy.yaml🟣 SOLO EN TS
Problema: Los 6 valores de VERIFICATION_OUTCOMES existen en taxonomy.ts y son usados en Alert.verificationOutcome e Incident.outcome, pero el YAML congelado no los documenta.
Impacto: El vocabulario maestro YAML (docs/14) sí los incluye en la sección A10, pero la fuente canónica oficial (docs/01) tiene un gap documental.
→ Acción: agregar verification_outcomes como nueva sección a docs/01-domain-taxonomy.yaml en la próxima versión del documento.
GAP-03Multi-tenant: residenciaId ausente en todas las entidades TypeScript🔴 GAP
Problema: La arquitectura de producción define residencia_id como el tenant isolator en todas las tablas. Ninguna interfaz en types.ts lo tiene. El MVP es single-tenant (localStorage) pero la transición a producción requeriría agregar el campo a todas las entidades.
Impacto: No es un blocker para el MVP demo, pero sí es un gap de diseño entre lo que los documentos de arquitectura dicen y lo que el código implementa.
→ Acción: documentar la decisión explícitamente en docs/03-data-model.md y en el vocabulario maestro. Candidato a v0.2 release.
GAP-04Rol manager mencionado en arquitectura y NOM-031 pero ausente en la taxonomía🔴 GAP
Problema: El documento docs/15-nom031-cobertura.html referencia el rol manager como quien accede al audit log completo y exporta bitácoras (R-08, R-30). La arquitectura evento-driven también lo menciona. Pero la taxonomía congelada y taxonomy.ts solo definen 3 roles: caregiver | supervisor | demo_admin.
Impacto: El acceso del "director técnico responsable" (NOM-031) no tiene un rol formal en la taxonomía. El supervisor puede estar haciendo funciones de manager en el MVP actual.
→ Acción: Decidir si manager es un alias de supervisor (con permisos extendidos) o un 4to rol. Implica change request al contrato §13 si se agrega. O corregir el lenguaje en los docs de arquitectura y NOM para usar supervisor consistentemente.
DIV-01Resident.monitoringFrequency: string vs nivel_cuidado ENUM⚠️ DIVERGENCIA
Problema: El campo se llama monitoringFrequency en el código pero el vocabulario de la arquitectura, la NOM-031 (dependencia funcional, R-10) y el vocabulario maestro lo llaman nivel_cuidado con valores bajo/medio/alto. Además es string libre, no un enum.
→ Acción v0.2: renombrar a careLevel o nivelCuidado + definir CARE_LEVELS = ['low','medium','high'] en taxonomy.ts.
DIV-02StaffMember.shift: string sin enum definido⚠️ DIVERGENCIA
Problema: El turno del personal es string libre. La NOM-031 exige control documentado de turnos (R-15). No hay constante SHIFTS ni tipo Shift en el vocabulario.
→ Acción v0.2: definir SHIFTS = ['morning','afternoon','night','on_call'] en taxonomy.ts.
DIV-03AuditEvent.action: string — los 20 tipos de evento no son un tipo literal⚠️ DIVERGENCIA
Problema: El vocabulario maestro (docs/14) define 20 tipos de audit_event como catálogo (ROUND_STARTED, ALERT_CREATED, etc.), pero AuditEvent.action en types.ts es string genérico. El compilador no puede verificar que solo se usen los 20 valores definidos.
→ Acción v0.2: crear AUDIT_EVENT_ACTIONS array + AuditEventAction tipo en taxonomy.ts, cambiar action: string a action: AuditEventAction.
DIV-04Round.completionNote?: string — resultado libre vs NOM requiere resultado documentado⚠️ DIVERGENCIA
Problema: La NOM-031 exige documentar el resultado de cada actividad de atención (R-01, R-19). El campo completionNote es texto libre — no es un enum controlado como VerificationOutcome.
→ Acción v0.2: agregar completionOutcome?: RoundOutcome con valores definidos (ej. ok, needs_follow_up, no_response, other).
DIV-05Inconsistencia de nomenclatura: in_verification (alerta) vs verification_in_progress (incidente)⚠️ DIVERGENCIA
Problema: El estado equivalente de "verificación en curso" se llama diferente en las dos máquinas de estado: in_verification en alertas y verification_in_progress en incidentes. El concepto es el mismo, la nomenclatura es inconsistente.
→ Es menor — ambos están en los docs y el código es funcional. Documentarlo en el vocabulario maestro como equivalencia intencional o unificar en v0.2.

CareSignal — Data Model & Arquitectura

📋 v0.2 — producción 🏗️ Event-driven · Multi-tenant · SaaS B2B 🗓️ Agosto 2026 ⚠️ MVP v0.1.0 usa localStorage — este doc define producción

01 Arquitectura event-driven

El sistema es event-driven con event sourcing parcial: cada acción significativa emite un audit_event inmutable. El estado actual de cualquier entidad se puede reconstruir reproduciendo su secuencia de eventos. El núcleo del negocio es la visita de cuidado (ronda) — cada cambio de estado de una ronda puede disparar alertas, escalar incidentes y registrar trazabilidad.

── Capas del sistema ────────────────────────────────────

Frontend  React + TypeScript
          └── 5 páginas por rol (caregiver / supervisor / manager)
          └── Estado local + suscripción a repositorio
          └── NO toca base de datos directamente

API       REST o tRPC
          └── Autenticación por residencia (tenant)
          └── Validación de transiciones (domain/transitions.ts)
          └── Emisión de audit_events en cada mutación

Dominio   Puro TypeScript — sin dependencias de infraestructura
          └── types.ts · taxonomy.ts · rules.ts · transitions.ts

Base de datos  PostgreSQL (producción) / localStorage (MVP demo)
          └── 9 tablas relacionales
          └── audit_events: append-only, nunca se edita

Motor temporal  Cron / worker
          └── Evalúa rondas cada N minutos
          └── Aplica 8 políticas automáticas (overdue, alertas)
          └── Emite eventos del sistema (no del usuario)

02 Raíz multi-tenant — residencia

Cada residencia es un tenant aislado. Todas las entidades llevan residencia_id como clave de aislamiento. Ninguna consulta cruza datos entre residencias.

residencia  (raíz del tenant)
    │
    ├── habitaciones   (infraestructura física)
    ├── residentes     (habitantes — asignados a habitación)
    ├── staff_members  (todos los usuarios: cuidador/supervisor/gerente)
    │
    ├── rondas         ← EVENTO CORE (visita de cuidado)
    │       └── pertenece a residente
    │       └── asignada a cuidador (0 o 1)
    │       └── tipo de ronda (lookup)
    │
    ├── alertas        (disparadas por rondas overdue)
    │       └── pertenece a residente
    │       └── owner: staff_member (0 o 1)
    │
    ├── incidentes     (registro formal de verificación)
    │       └── vinculado a alerta
    │
    └── audit_events   (log inmutable — append only)
EntidadCardinalidadNotas
residencia → habitaciones1 : NUna residencia tiene muchas habitaciones
habitacion → residentes1 : NUna habitación puede tener 1–N residentes según capacidad
residente → rondas1 : NUn residente tiene muchas rondas a lo largo del tiempo
staff_member → rondas1 : NUn cuidador puede tener 0–N rondas asignadas
ronda → alerta1 : 0..1Una ronda overdue puede generar una alerta (máx. una activa)
alerta → incidente1 : 0..1Una alerta puede derivar en un incidente formal
cualquier entidad → audit_events1 : NToda acción emite un evento; el log es append-only

03 Evento core — la visita de cuidado (ronda)

La ronda es el hecho central del sistema. Cada ronda es una visita programada de un cuidador a un residente. Su ciclo de vida completo define si el cuidado ocurrió, cuándo y con qué resultado — y es la única fuente de verdad para la trazabilidad operativa.

Máquina de estados

scheduled → due → in_progress → completed
due → overdue → 🔔 ALERTA
scheduled → cancelled — no genera alerta

Transiciones válidas e inválidas

07 API layer — endpoints principales

Todas las rutas requieren residencia_id en contexto de sesión. Ningún endpoint acepta datos de otra residencia.

── Rondas ────────────────────────────────────
GET    /rondas?estado=due,overdue&turno=actual
POST   /rondas                          ← programar nueva ronda
PATCH  /rondas/:id/start                ← caregiver inicia
PATCH  /rondas/:id/complete             ← caregiver completa + resultado
PATCH  /rondas/:id/cancel

── Alertas ───────────────────────────────────
GET    /alertas?estado=open,assigned
PATCH  /alertas/:id/acknowledge
PATCH  /alertas/:id/assign              ← body: { owner_id }
PATCH  /alertas/:id/escalate
PATCH  /alertas/:id/start-verification
PATCH  /alertas/:id/resolve             ← body: { resultado_verificacion }
PATCH  /alertas/:id/close

── Residentes ────────────────────────────────
GET    /residentes                       ← incluye estado_visual derivado
GET    /residentes/:id                   ← detalle + últimas rondas

── Auditoría ─────────────────────────────────
GET    /audit?entidad_tipo=ronda&entidad_id=:id
GET    /audit?desde=ISO&hasta=ISO         ← solo gerente

── Motor temporal (interno, no expuesto al cliente) ──
POST   /internal/tick                    ← cron cada N min

Cada mutación: (1) valida transición en domain/transitions.ts, (2) escribe a la tabla, (3) inserta en audit_events — todo en una transacción.

09 Ciberseguridad

Los datos de adultos mayores son datos sensibles por ley bajo la LFPDPPP (Ley Federal de Protección de Datos Personales en Posesión de los Particulares). El diseño de seguridad es privacidad por diseño: el dato más seguro es el que nunca sale del dispositivo — decisión mantenida en v0.1.0 y aplicada como ventaja diferenciadora frente a soluciones cloud-first.

Principios de diseño de seguridad

PrincipioImplementaciónConexión con sección
Aislamiento de tenantCada query lleva residencia_id. Ningún dato cruza entre residencias — enforced en API layer.§02 Multi-tenant, §07 API
Control de acceso basado en roles (RBAC)Cada endpoint valida el rol del actor. Caregiver no puede cerrar alertas; supervisor no puede ver auditoría completa; gerente no ve otra residencia.§06 Vistas / roles
Audit log inmutableaudit_events: solo INSERT, nunca UPDATE ni DELETE. Toda acción con actor, timestamp, payload. Es evidencia legal ante inspección.§04 Data model, §05 Eventos
Privacidad por diseño (v0.1.0)En el MVP, ningún dato sale del dispositivo (localStorage). No hay API externa, no hay sincronización. La ausencia de red es la mejor defensa.§08 Repo público
Cifrado en tránsito (v0.2)HTTPS/TLS en toda comunicación. Google Cloud Run fuerza TLS. Firebase usa cifrado en tránsito por defecto.§07 API layer
Cifrado en reposo (v0.2)GCP cifra datos en reposo por defecto (AES-256). Firebase Storage y Firestore cifran en reposo sin configuración adicional.§04 Data model
Minimización de datosEl MVP usa datos ficticios. En producción: ningún campo que no sea estrictamente necesario para la operación. estado_visual del residente no se persiste — es derivado.§04 Data model

Arquitectura de seguridad v0.2 — GCP + Gemini

── Capas de seguridad en producción ──────────────────────

Perímetro
  └── HTTPS/TLS obligatorio — Google Cloud Run
  └── Autenticación: Firebase Auth (JWT firmado por Google)
  └── Autorización: middleware RBAC en cada endpoint

Datos en reposo
  └── PostgreSQL / Firestore: AES-256 (GCP por defecto)
  └── audit_events: particionado por residencia_id + fecha
  └── Backups cifrados automáticos

Datos en tránsito
  └── TLS 1.3 en todas las conexiones
  └── Tokens JWT con expiración corta (1h access / 7d refresh)
  └── Headers: HSTS, CSP, X-Frame-Options

Agente de ciberseguridad (Gemini API)
  └── Monitorea patrones anómalos en audit_events
  └── Detecta: accesos fuera de turno, cambios en masa, escalaciones inusuales
  └── Genera alertas internas al gerente — no al residente
  └── NO procesa datos identificables — solo metadatos de eventos

Aislamiento multi-tenant
  └── Row-Level Security (RLS) en PostgreSQL por residencia_id
  └── Firebase Security Rules: cada documento lleva /residencias/{id}/
  └── Ningún query devuelve datos de otro tenant

10 Assessment — IA, Machine Learning y Chatbots

Esta sección evalúa la aplicabilidad real de tres familias de tecnología de IA para CareSignal. El criterio no es si la tecnología existe, sino si resuelve un problema real del usuario a un costo y complejidad justificados, dado el volumen de datos y el contexto operativo actual.

VeredictoSignificado
✅ APLICABLEResuelve un problema real hoy. Implementable en v0.2 con los datos y arquitectura disponibles.
⏳ DIFERIRVálido en el futuro, pero requiere datos reales que aún no existen. Implementar ahora es construir sin cimiento.
❌ SOBREDIMENSIONADOLa tecnología existe pero el problema ya tiene una solución más simple, más barata y más confiable.
🔬 PREMATURORequiere validación con usuarios reales antes de diseñar. Riesgo de construir la función equivocada.

A. Machine Learning

ML supervisado requiere datos históricos etiquetados — al menos 6–12 meses de operación real con outcomes conocidos. En v0.1.0 los datos son ficticios; en v0.2 los primeros pilotos generarán datos reales pero insuficientes para entrenar modelos. Las reglas deterministas del motor temporal (8 políticas) superan a cualquier modelo ML cuando el volumen de datos es bajo.

Función MLProblema que resuelveDatos necesariosDisponibilidadVeredicto
Alertas predictivas de ronda Predecir qué rondas van a retrasarse antes de que ocurra el retraso Histórico de tiempos por cuidador, residente, turno y tipo de ronda — mínimo 3 meses de operación real ❌ No existe en v0.1.0 ni en los primeros pilotos ⏳ DIFERIR v0.3+
Detección de anomalías en audit log Identificar patrones de operación fuera de lo normal (accesos raros, escalaciones inusuales) Baseline de comportamiento normal — requiere semanas de datos reales etiquetados ❌ Sin baseline no hay anomalía detectable ⏳ DIFERIR v0.3+
Optimización de asignación de cuidadores Asignar cuidadores a rondas minimizando tiempo de respuesta y carga de trabajo Datos de disponibilidad, carga histórica, preferencias — requiere múltiples residencias para generalizar ❌ Un solo piloto no tiene señal suficiente ⏳ DIFERIR v0.3+

Conclusión ML: Ninguna función de ML es aplicable en v0.2. La arquitectura event-driven (audit_events con 20 tipos) está diseñada para ser el insumo futuro de estos modelos — pero los modelos necesitan datos reales primero. El motor temporal determinista es la solución correcta para v0.2.

B. Agentes de IA (3 tipos)

Un agente de IA es un sistema que percibe contexto, decide una acción y la ejecuta — opcionalmente en bucle. Para CareSignal, los agentes más relevantes son los que actúan sobre el flujo de eventos sin necesidad de datos históricos de entrenamiento.

Elimina trabajo manual del supervisor al cerrar turno — alto valor, bajo riesgo

Conclusión agentes: El agente operativo ya está resuelto por reglas deterministas — no necesita IA. Los agentes A2 y A3 son los candidatos reales para v0.2: operan sobre metadatos de eventos ya existentes, no requieren datos históricos de entrenamiento y tienen valor directo para supervisores y gerentes.

C. Chatbots (3 tipos)

Un chatbot agrega valor cuando el usuario necesita consultar información no estructurada o cuando la UI alternativa sería un formulario complejo. Para CareSignal, la pregunta es si un cuidador o supervisor prefiere escribir una pregunta o tocar un botón en pantalla — en operaciones de cuidado urgente, la respuesta casi siempre es el botón.
